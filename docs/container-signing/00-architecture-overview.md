# 00 — Container Image Signing: Architecture Overview

> **Scope:** signing container images with **Venafi CodeSign Protect 24.1** keys, from **CloudBees CI**
> pipelines, using **cosign**, pushing to **Harbor**, with all credentials brokered by **HashiCorp Vault
> Enterprise**. Runtime enforcement is **Sigstore Policy Controller**.
>
> **Key custody:** no HSM. Private keys live in the **CodeSign Protect Secret Store** on the Trust
> Protection Platform (TPP) server. No key material ever reaches a build agent.
>
> **Audience:** platform engineering, CI engineering, PKI/Venafi administrators, container platform
> (Kubernetes) operators, and application security.

---

## 1. Why this design

Today cosign would need a private key on the build agent. That key would be readable by anyone with
agent access, exfiltratable, unauditable, and impossible to revoke cleanly. Venafi CodeSign Protect
removes the key from the agent entirely: the agent sends a **hash** to TPP and receives a **signature**
back. The key never leaves the server.

Venafi is explicit about the division of labour:

> **IMPORTANT** — The role of Venafi CodeSign Protect is to protect private code signing keys and to
> govern the use of those keys. Venafi CodeSign Protect itself does not sign code.
>
> — [CodeSign Protect architecture, 24.3](https://docs.venafi.com/Docs/24.3/TopNav/Content/CodeSigning/c-codesigning-architecture.php)

Read that carefully, because it explains the whole integration: **TPP returns a signed hash; cosign
composes the signature envelope and writes it to Harbor.** cosign remains the tool that understands OCI;
Venafi is purely the key custodian and policy engine.

---

## 2. Key storage — the "no HSM" decision

Our environment does **not** use an HSM, and is **not** permitted to use SoftHSM. This is fully supported.
Per the architecture documentation, the CodeSign Protect components are:

- Trust Protection Platform server with CodeSign Protect enabled
- Venafi Code Signing clients on Windows / Linux / macOS signing workstations
- *"**Optionally**, a Hardware Security Module (HSM) connected to the CodeSign Protect server"*

and:

> All code signing private keys are stored in either the **CodeSign Protect Secret Store** or in an
> attached HSM.

So with no HSM attached, keys are generated by TPP and held in the **CodeSign Protect Secret Store**,
with signing operations serviced by the **Venafi software encryption driver**.

> **This is not SoftHSM.** The prohibition in our standards refers to the OpenSC **SoftHSM2** library — a
> software PKCS#11 token that holds key material in a file *on the client*. The CodeSign Protect Secret
> Store is a **server-side**, TPP-managed, access-controlled and audited key store. The build agent holds
> no key material in either case, and the two are unrelated technologies. Record this distinction in the
> control narrative — it is the single most likely point of confusion in an audit review.

---

## 3. Why PKCS#11 (this is not a preference)

The Code Signing Connector matrix is:

| Platform | Available connectors |
|---|---|
| Windows | CSP/KSP, PKCS#11, GPG |
| Linux | **PKCS#11, GPG** |
| macOS | PKCS#11, Keychain Access, GPG |

Our build agents are Linux. GPG is not a cosign signing backend. **PKCS#11 is therefore the only path**,
and no evaluation of alternatives is required for the Linux CI use case.

The Venafi PKCS#11 module is *not* a local token — it is a remote-signing shim that forwards operations
to TPP over a TLS-encrypted REST API. You can see this in the token name it presents: **`Remote Token`**.

> **Version note.** The Venafi "Sigstore cosign integration" page is **identical in 24.3, 25.1, 25.3 and
> 26.1** apart from the CyberArk rebrand (*Venafi CodeSign Protect* → *Code Sign Manager - Self-Hosted*,
> *CodeSign Protect client* → *Code Sign Client*). Same prerequisites, same commands. **Do not couple this
> project to a platform upgrade** — upgrading gains nothing for container signing. Where this SOP says
> "CodeSign Protect", read "Code Sign Manager - Self-Hosted" on 25.3+.

## 4. End-to-end flow

```
  ┌────────────────────────── CloudBees CI controller ──────────────────────────┐
  │  Build job (static Linux VM agent, see 02)                                  │
  │                                                                             │
  │  1. mint OIDC ID token  ─────────────────►  Vault Enterprise (ns: AUT)      │
  │  2. exchange for Vault token (JWT auth)  ◄─────────  scoped, 15m TTL        │
  │  3. read secrets: Venafi svc acct, Harbor robot, Prisma creds               │
  │                                                                             │
  │  4. podman build                                                            │
  │  5. twistcli scan  ──────────────────────►  Prisma Cloud Console            │
  │     └─ non-zero exit on threshold breach  ⇒  FAIL, never sign               │
  │  6. podman tag + podman push  ───────────►  Harbor (build project)          │
  │     └─ capture sha256 digest                                                │
  │                                                                             │
  │  7. pkcs11config getgrant  ──────────────►  TPP /vedauth                    │
  │  8. cosign sign <repo>@sha256:<digest>                                      │
  │     └─ hash ────────────────────────────►  TPP /vedhsm  (Secret Store key)  │
  │     └─ signature ◄──────────────────────   signed hash returned             │
  │     └─ signature artifact  ─────────────►  Harbor (.sig accessory)          │
  │  9. cosign verify (gate)                                                    │
  │ 10. pkcs11config revokegrant  (always, in post{})                           │
  └─────────────────────────────────────────────────────────────────────────────┘
                                        │
                                        │ promote / replicate (signature follows)
                                        ▼
                              Harbor (production project)
                                  enforcement enabled
                                        │
                                        ▼
                    Kubernetes admission — Sigstore Policy Controller
                    ClusterImagePolicy verifies against Venafi public key
```

Steps 7–10 are the new work. Steps 4–6 already exist in our pipelines.

## 5. Trust boundaries

| Boundary | Crossing | Control |
|---|---|---|
| CI agent → Vault | OIDC ID token (per build, short-lived) | JWT auth role bound on issuer + `job` claim; 15m token TTL |
| CI agent → TPP `/vedauth` | Service account credential from Vault | Grant is per-user, time-limited, revoked in `post{}` |
| CI agent → TPP `/vedhsm` | Image manifest **hash only** | No key material returns; TPP enforces key-use policy per environment |
| CI agent → Harbor | Robot account from Vault | Scoped to one project, push + pull only |
| CI agent → Prisma Console | Service credential from Vault | Read/scan only |
| Harbor → Kubernetes | Signed image + `.sig` accessory | Policy Controller verifies signature against the Venafi public key |

**The security claim this design supports:** an attacker with root on a build agent can request signatures
while a grant is live, but cannot extract the signing key, cannot sign after the grant is revoked, and
cannot sign without leaving an entry in the CodeSign Protect audit log attributable to the CI service
account. Sign-request abuse is detectable; key theft is prevented.

> **Residual risk to document and accept:** during the window between `getgrant` and `revokegrant`, a
> compromised agent can sign arbitrary content. Mitigate with short grant lifetimes, a dedicated signing
> agent label (see `02`), restricted `Job/Configure` permissions on the signing job, and alerting on
> signing volume anomalies in the Venafi audit log. This risk is inherent to any remote signing service
> and is materially smaller than key-on-disk.

| Venafi CodeSign Protect client (Linux) | 21.4 or newer | PKCS#11 connector; pin one version fleet-wide |

## 9. Validation status

This SOP is written from vendor documentation. Two items **must be confirmed against the installed client**
before production sign-off; both are flagged inline where they appear:

1. Whether the Venafi PKCS#11 module honours RFC 7512 `pin-source=<file>` (avoids PIN on the command
   line) — `02 §5`, `04 §7`.
2. The supported mechanism for isolating concurrent signing operations on a shared agent — `02 §6`.

Everything else is either documented by the vendor or is standard cosign/Harbor/Kubernetes behaviour.
